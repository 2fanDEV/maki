# maki

Run `cargo run` to start the server at `127.0.0.1:3000`.

## OpenAPI

Open `http://127.0.0.1:3000/swagger` for Swagger UI, which loads the generated
specification and lets you explore and call the API.

`GET /openapi.json` serves the OpenAPI 3.1 specification generated by Aide from
the service routes and Rust request/response schemas. For example:

```sh
curl http://127.0.0.1:3000/openapi.json
```

The spec includes model creation, polling, errors, and SSE. SSE is described as
`text/event-stream`; its `x-sse-data-schema` extension describes the JSON data
inside each event. The existing document endpoints are marked as placeholders.

Register documented routes through `Service::api_router()` using Aide's
`api_route` methods, and derive `schemars::JsonSchema` on their API types.
The application combines these routes before generating the spec once at startup.
Each service keeps routing and HTTP handling in `api/mod.rs`, API inputs in
`api/request.rs`, and outputs in `api/response.rs`. The parent `mod.rs` contains
service logic and orchestration. See [AGENTS.md](AGENTS.md) for the convention.

## Create a classifier

`POST /models` creates a model and returns its model ID immediately. Training and
evaluation run outside the HTTP runtime, so polling and SSE remain responsive.

Clients must specify `classifier`. Currently the supported value is
`nearest_centroid`; missing or unsupported values return `400`. Documents contain
extracted text pages and finite numeric class labels. Every class needs at least
two documents.

```sh
curl -s http://127.0.0.1:3000/models \
  -H 'Content-Type: application/json' \
  -d '{
    "classifier": "nearest_centroid",
    "documents": [
      {"name":"fruit-a", "pages":["apple sweet fruit"], "label":0},
      {"name":"fruit-b", "pages":["apple fresh fruit"], "label":0},
      {"name":"vehicle-a", "pages":["car road vehicle"], "label":1},
      {"name":"vehicle-b", "pages":["car fast vehicle"], "label":1}
    ],
    "split": {"ratio":0.8, "repetitions":20, "sampling":"stratified"},
    "tf_idf": {"tf_scheme":"raw_count", "idf_scheme":"base", "double_normalization_k":0.5},
    "evaluation_strategy":"macro_f1",
    "seed":42
  }'
```

`classifier` and `documents` are required. Optional settings default to an 80%
training ratio, five stratified splits, base/raw-count TF-IDF, and macro-F1.
An omitted seed is generated and returned. The Rust builder retains its default
of one split. `repetitions: 1` requests one split through HTTP.

The response is `202 Accepted`:

```json
{
  "model_id": "<uuid>",
  "seed": 42,
  "status_url": "/models/<uuid>",
  "events_url": "/models/<uuid>/events"
}
```

| Endpoint | Purpose |
|---|---|
| `POST /models` | Create a model |
| `GET /models/{model_id}` | Poll model progress, metadata, errors, and evaluation results |
| `GET /models/{model_id}/events` | Observe the same model through SSE |

For SSE, use `curl -N http://127.0.0.1:3000/models/<uuid>/events`.

## Percentage progress owned by Trainer

The builder prepares the full collection of train/test splits and passes it to
`Trainer`. The trainer owns training, evaluation, and progress. Its percentage is:

```text
percentage = successfully trained splits / total received splits * 100
```

For twenty splits, the trainer emits 0%, 5%, 10%, and so on through 100%. A failed
fit does not advance the count. The same percentage appears in polling and SSE:

```json
{
  "progress": {
    "state": "running",
    "trained_splits": 1,
    "total_splits": 20,
    "percentage": 5.0
  }
}
```

There are no per-row or per-phase counters. Evaluation does not contribute to the
percentage: 100% means all classifiers trained successfully; `completed` means
evaluation and selection also finished and the selected model is accessible.
A failed evaluation retains the percentage of successfully trained splits.

Before the trainer receives the actual splits, progress is `initialized`, 0%,
with `total_splits: 0`. The trainer supplies the real denominator when it starts.
Failures expose `progress.state: "failed"` and an `error` on the model metadata.

Polling and SSE expose the latest model data. SSE event names are `progress`,
`completed`, and `failed`; the stream closes after the terminal update. A reconnect
receives the latest data rather than an event history. Slow readers may skip
intermediate percentages. Disconnecting an observer does not cancel creation.

## Evaluation and selection

The trainer computes `macro_f1`, `balanced_accuracy`, and `matthews_correlation`
for every split's training and test predictions. Reports contain absolute gaps,
actual partition sizes, means, and population standard deviations across splits.

Selection chooses the highest test score for the configured metric, then the
smallest train/test gap on an exact score tie, then the lowest split index.
These are **held-out selection scores**, not an independent final-test estimate.
The winner retains its matching fitted TF-IDF, without retraining on test data.

Stratified sampling shuffles each class independently and assigns
`floor(class_count * ratio)` documents to training, clamped to leave at least one
sample of every class in each partition. This can change the effective ratio for
small classes. `sampling: "random"` uses unstratified partitioning; classes may be
absent from a partition. Evaluated training requires a ratio strictly between zero
and one and nonempty training/test partitions.

TF-IDF is fitted only on training documents. Test documents are transformed using
that fitted state and never passed to classifier training. A fixed seed and
identical input/settings reproduce splits within the same implementation/version.

TF schemes: `binary`, `raw_count`, `normalization`, `double_normalization_half`,
`double_normalization_variable`. IDF schemes: `base`, `smooth`, `maximum`,
`probabilistic`. The double-normalization constant must be within `[0, 1]`.

## Storage and Rust API

Model metadata, progress, reports, and fitted models are kept only in memory.
They are lost on restart. No persistence, model-download, or HTTP inference
endpoint is included. `ClassificationService::model(model_id)` returns the fitted
classifier and its TF-IDF once creation succeeds, using the original model ID.

Invalid JSON/request shapes return `400`; invalid training settings return `422`;
unknown model IDs return `404`. Errors during training/evaluation remain available
through the model's polling and SSE endpoints.

`TrainerBuilder::build()` prepares splits and delegates to the trainer constructor.
Configure an observer with `progress_observer`; only `Trainer` emits updates.
Read final progress with `Trainer::progress()` or `TrainingOutcome::progress`.
Model factories receive `(training_documents, features)` and return a classifier.
The default factory still returns `Missing model generating function!`.
`Classifier::train` trains one classifier; it does not estimate trainer progress.
`Classifier::predict(&features)` accepts the sparse feature matrix and returns one
label per document row, in row order.
Evaluated documents implement both `Document` and `LabeledDocument`.

Run `cargo test`, `cargo fmt --check`, and `cargo clippy --all-targets` to verify.
